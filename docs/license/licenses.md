# 주요 오픈소스 라이선스 비교

## 분류
| 유형 | 핵심 조건 | 대표 라이선스 |
|---|---|---|
| 허용형(Permissive) | 저작권·라이선스 고지 유지. 독점 SW에 포함 가능 | MIT, BSD 2/3-Clause, Apache 2.0 |
| 약한 카피레프트 | 해당 파일·라이브러리의 수정분만 공개 | LGPL, MPL 2.0, EPL 2.0 |
| 강한 카피레프트 | 결합한 파생 저작물 전체를 같은 라이선스로 공개 | GPL v2, GPL v3 |
| 네트워크 카피레프트 | 네트워크로 서비스만 제공해도 소스 공개 | AGPL v3 |
| 퍼블릭 도메인 수준 | 사실상 조건 없음 | CC0, Unlicense |

## 주요 라이선스별 의무
| 라이선스 | 고지 의무 | 소스 공개 범위 | 특허 조항 | 비고 |
|---|---|---|---|---|
| MIT | O | 없음 | 없음 | 가장 짧고 단순. React, Node.js 등 |
| BSD 3-Clause | O | 없음 | 없음 | 저작자 이름의 홍보 사용 금지 |
| Apache 2.0 | O (NOTICE 파일 포함) | 없음 | 명시적 특허 허락·특허 보복 조항 | 기업 선호. Kubernetes, Android 일부 |
| MPL 2.0 | O | 수정한 파일 | 있음 | 파일 단위 카피레프트. Firefox |
| LGPL | O | 수정한 라이브러리 | v3에 있음 | 동적 링크 시 앱 코드 공개 불필요 |
| GPL v2 | O | 파생 저작물 전체 | 묵시적 | 리눅스 커널 |
| GPL v3 | O | 파생 저작물 전체 | 있음 | 티보이제이션(하드웨어 잠금) 금지 |
| AGPL v3 | O | 파생물 + 네트워크 서비스 | 있음 | SaaS에도 공개 의무 |

## 라이선스 호환성 요점
- 허용형 코드는 대부분 카피레프트 프로젝트에 넣을 수 있지만, **반대는 불가**합니다.
- Apache 2.0은 GPL v3와는 호환되지만 **GPL v2(only)와는 호환되지 않습니다.**
- 여러 라이선스를 섞을 때는 가장 강한 의무를 기준으로 판단합니다.

## 소스 어베일러블(오픈소스가 아닌 것)
최근 클라우드 기업의 무임승차에 대응해 일부 기업이 OSD를 충족하지 않는 라이선스로 전환했습니다.
- **SSPL**: MongoDB(2018), Elastic(2021, 이후 2024년 AGPL 옵션 추가)
- **BSL(Business Source License)**: HashiCorp Terraform(2023) → 커뮤니티가 **OpenTofu**로 포크
- Redis(2024) 라이선스 변경 → **Valkey** 포크, 이후 Redis 8(2025)에서 AGPL 옵션 추가

## 실무 체크리스트
1. 사용하는 오픈소스와 라이선스 목록(SBOM)을 만든다.
2. 배포 형태(내부 사용, 제품 배포, SaaS)를 확인한다. 의무는 **배포**에서 발생하는 경우가 많다.
3. 고지문(저작권, 라이선스 전문)을 제품·문서에 포함한다.
4. GPL·AGPL 계열은 결합 방식(정적/동적 링크, 별도 프로세스)을 검토한다.
5. 국내 무료 도구(OLIS, 코드아이, 오소리 DB)로 검증한다 → [부록: 국내 정책·지원 사이트](../appendix/policy-sites.md)
